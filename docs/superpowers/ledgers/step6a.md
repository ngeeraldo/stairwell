## Built

`lib/db/encryptedUserDb.ts` opens (or lazily creates) `users/<slug>/<slug>.db`
with `db.key(Buffer)` over a pinned `chacha20` cipher, executes that user's
`schema.sql` as the first statement so the key check and the schema apply are
the same operation, and names `WrongKeyError` for the one case the driver
cannot distinguish on its own — a wrong key and a corrupt file are both
`SQLITE_NOTADB`, and only the opener knows whether the file existed a moment
ago. A failed create unlinks its own debris, because `new Database(path)`
writes real bytes before the key is validated and a left-behind stub would make
the *correct* key report as wrong forever after.

`POST /api/users/[user]/walk` is the only write path in the repo. Four checks in
a fixed order — unlocked, then ownership (404, never 403), then a registered
dashboard, then key/open/write/close — and an `INSERT OR IGNORE` keyed on the
local day, so a double tap is a no-op with no read-then-write race.

`app/[user]/page.tsx` resolves three states rather than two: real data when a
key exists and the file exists, synthetic under the banner otherwise, and
"not generated yet" when neither file is there. The encrypted open sits inside
the try, and the handle is closed in a `finally` — opened per request, never
cached, because a handle is scoped to one key and a key to one session.

`users/devtwo/` is the second worked dashboard and the first one built from a
confirmed spec: `schema.sql`, `seed.py`, `queries.ts` (reads only), a
`dashboard.tsx` of one component with plain helpers, and a `tests/` folder,
plus the registry line.

**Seven rulings:**

1. **Step 6 split into 6a/6b** — Nico's, 2026-08-13. Encryption lands before
   the first real byte rather than after it. It is the only ordering the
   onboarding promise supports.
2. **The real database is created lazily on first write**, not at login — so
   devone's reference dashboard is never handed an empty real file and keeps
   reading the sample it was built against.
3. **`dashboard_write` carries a slug and a panel and never a value.** Adopted
   as permanent policy for every future panel type, not as this route's local
   choice. For this dashboard "they tapped" and "they walked the dog" are the
   same fact, and `metrics` is the unencrypted platform database. This row is
   what makes the login page's "I can see when you use it … but not what you
   log" true. Observed directly: `dashboard_write|{"slug":"devtwo","panel":"walked_today"}`.
4. **`db.key(Buffer)`, never a `key=` pragma**, and the cipher pinned rather
   than inherited. A pragma turns 32 bytes of key material into a SQL string on
   its way through the driver; an inherited default means a driver upgrade
   could make every existing file report as corrupt.
5. **No caching of encrypted handles.** Opened per request, closed in a
   `finally`. Step 5's residual 4 warned that `openUserDb`'s process-wide cache
   is correct only for a read-only file that changes at deploy.
6. **Step 6a's checkpoint depends on nothing from step 4 that has not now been
   exercised.** Step 4's spec flow produced `devtwo`'s confirmed spec, that
   spec was pulled into the repo, and `users/devtwo/` was built from it. There
   is no step-4 mechanism left standing untested behind this checkpoint.
7. **The dashboard has no styling and does not resemble `mockup.html`, and
   that is out of scope for 6a.** Controller's ruling. It is platform-wide —
   there is no CSS anywhere in `app/`, devone renders equally bare, and Nico
   confirmed all five step-5 checkpoints against that bare rendering. Inventing
   a styling layer mid-plan is the unasked-for widening the plan forbids.
   Carried as residual 8 and raised to Nico as a scope question, because
   `users/devtwo/spec.md` records that he asked repeatedly for the preview.

## What the review layer caught

**The headline is a defect neither task's review could have found, because it
did not exist in either task.**

**The tap control was absent on handover morning.** `dashboard.tsx` hides the
form when today is already walked, and before the first real tap that `done`
comes from `synthetic.db`. `seed.py`'s `MISSED` set omitted `0`, so the sample
always said today was walked. `deploy.sh` regenerates `synthetic.db` on every
deploy. A friend logging in the next morning would have met **"WALKED / Marked
for today."** — a false statement about their own dog — with no tap control at
all, on the only write path there is. It also contradicted the mockup they
approved, whose today panel reads NOT YET with the pill.

Task 4 shipped the seed. Task 5 shipped the component. **Each half is correct
alone.** Task 4's review had no component to hide anything; Task 5's review had
a component whose conditional is plainly right. The defect exists only in the
composition, and only on one morning. Fixed by adding `0` to `MISSED`, with the
reason written into `seed.py` beside it, and pinned by
`users/devtwo/tests/seed.test.ts` — which spawns the real `python3 seed.py`
through `execFileSync` into a temp database and asserts today is unwalked in
the *generated* file, because a hand-built fixture would not have caught it
either. The re-reviewer reproduced the original bug from a reverted copy before
accepting the fix.

**The lesson, recorded as a rule: review the composed product, not only the
diff.** A per-task review is a review of a diff. This defect had no diff.

The rest, in the order they were found:

- **A failed create poisoned the wrong-key diagnosis permanently.** The driver
  creates the file and writes pragma bytes before the key is validated, so a
  failed open on a brand-new file left a 4096-byte stub — making `existedBefore`
  true on the retry and reporting the *correct* key as `WrongKeyError` forever.
  Found by probing, not by reading. A lockout, in the one place where a lockout
  is unrecoverable by design.
- **The cipher-pinning test could not fail.** The pinned value equals the
  driver's default, so deleting the pin changed nothing observable. The reviewer
  found `step1a.md` had already recorded the identical pattern for
  `deriveDbKey`'s Argon2id pin and deferred it — second occurrence, so not
  deferred again. Now asserts the *call*, not the outcome.
- **The ordering property of the walk route's four checks was pinned by
  nothing, and both the test comment and the commit message said it was.** The
  plan's proposed assertion ("no key fetched") could never have discriminated,
  because `resolveState` fetches the key internally — the plan asked for
  something unachievable. Now spies on `canSeeUserSpace`, the one observable
  that exists only if check 1 failed to short-circuit.
- **`dayKey` was exported for testability with zero tests**, and the round-trip
  test compared the written row against the same `dayKey` used to write it, so
  a UTC regression was invisible. Now tested under three timezones, with the
  test stating honestly that at UTC the divergence case asserts nothing further.
  (This is also the export that breaks Gate D. It was reviewed twice, by people
  looking hard at it, and neither pass asked whether a route module may export
  it.)
- **`openEncryptedUserDb` sat OUTSIDE the try in both the page and the walk
  route**, so a `WrongKeyError` would have 500'd the whole route and taken the
  chat surface with it — the surface that exists so a friend can report that
  the dashboard broke. Systemic, not a single task's regression.
- **The fix for that introduced a metrics leak**, writing raw `error.message`
  into append-only metrics — while the route's catch, in the same round,
  deliberately did not. Caught because a reviewer read `step5.md`, found
  residual 6 predicting this exact trigger, and checked whether it had come
  true. See "What the ledger caught" below.
- **The streak panel was pinned by nothing, in the test whose title claimed
  it.** Deleting the entire panel left all four tests green — the exact mutation
  the file's own header says it exists to catch, on the panel Nico asked for by
  name. The 14-day panel was counted and never valued: fourteen hard-coded
  `<li data-day="x" data-walked="no">` passed. The replacement was drilled
  adversarially with correct days in reversed order, and still failed.
- **A brief's hand-written test assertions were wrong twice.** Task 5's brief
  assumed `JSON.stringify` concatenates adjacent JSX children and serialises
  props as `key=value`; neither is true. The implementer fixed the test rather
  than degrading the component. Both times the controller had written
  assertions it had not run — the same defect class as a commit message
  predicting a drill outcome, which also happened here (`1b47511`, amended).

## Residual risks

1. **`npx next build` fails at `4cf75b8`** — the open blocker above. Not a risk;
   a known break, unfixed on this branch, blocking both push and deploy.
2. **Gate C's verdict depends on whether `.next/types` exists**, and that
   directory is gitignored build output. A clean checkout typechecks green on a
   branch that does not build. Running a build before the typecheck changes the
   answer. Nothing in `.githooks/pre-commit` establishes that state.
3. **A forgotten password destroys the data.** No reset, no backup, by design.
   Now stated on the login page. The `rm users/devtwo/devtwo.db` reset in
   `docs/local-dev.md` is the same property, deliberately.
4. **`<slug>.db` is not backed up at all.** A droplet loss is a data loss. There
   is no backup mechanism anywhere in `deploy/`, and an encrypted file that only
   the user's password opens is not something the operator can back up usefully
   without a design decision nobody has made yet.
5. **Nothing verifies the DEPLOYED file is encrypted.**
   `tests/db/encryptedUserDb.test.ts` byte-checks a file it creates in a temp
   tree — that proves the opener encrypts, not that the file on the droplet is
   encrypted. `head -c 16 users/devtwo/devtwo.db | xxd` must be run once on the
   droplet against the first real `devtwo.db`. It is documented in
   `docs/local-dev.md` and it is a human's job: CLAUDE.md forbids Claude opening
   any `*.db` that is not `synthetic.db`, and that includes this one.
6. **The wrong-key narrowing (`notADb && existedBefore`) is reasoned, not
   test-pinned.** Widening it to `notADb` alone breaks no test. The plan
   expected this drill to come back green; it did. The answer is this line, not
   a new test.
7. **The `db.close()` in the page's `finally` is not test-pinned.** A leak
   surfaces as file handles, not as a failing assertion. Same shape as
   `closeUserDbs` in step 5's fix wave, which was green while leaking a
   descriptor per `afterEach`.
8. **The dashboard has no styling and does not resemble
   `users/devtwo/mockup.html`.** Ruling 7 above; out of scope, raised to Nico as
   a scope question. Same family: the page renders the raw `YYYY-MM-DD` day key
   where the mockup humanises the date, and titles itself with the slug where
   the mockup carries its own title and subtitle.
9. **A dashboard's real-path handle is NOT read-only.** `openEncryptedUserDb`
   has no readonly mode, because the same call creates the file and applies the
   schema. On the synthetic path the handle is `readonly: true`; on the real
   path a dashboard component could write. CLAUDE.md's convention bullet
   previously claimed a read-only handle unconditionally and has been corrected.
   Nothing enforces the convention but review.
10. **`seed.py`'s loud-fake sentinel puts a non-day value
    (`'1970-01-01 SAMPLE TEST'`) in the `day` PRIMARY KEY**, contradicting what
    `schema.sql` documents that column to be. Harmless — both window queries are
    string range comparisons that exclude it — and recorded in the file's own
    comment rather than left to be rediscovered.
11. **`dayKey` (route) and `dayKeyOf` (devtwo queries) are the same computation
    in two modules, deliberately.** A platform route must not import one user's
    queries file. The duplication is accepted; nothing pins the two against each
    other, so they can drift.
12. **A production `dashboard_error` with `kind: 'error'` gives an operator no
    way to tell a permissions failure from a corrupt file.** Not a regression —
    the prior code had no server-side log either. The right fix is
    `console.error` at the catch site, which never reaches the append-only
    table. **NOT widening `kind`**, which would walk the leak back in.
13. **`users/devtwo/queries.ts` holds only reads**, though its header once said
    "every SQL statement". The INSERT lives in the platform walk route by
    design. Wording corrected; the asymmetry with `CLAUDE.md > Dashboard folder
    conventions` ("`queries.ts` — every SQL statement") remains.
14. **Step-4 residual 8 is unchanged and now costs more.** `devone` and `devtwo`
    are live production logins with passwords published in `docs/local-dev.md`,
    and as of this step one of them can create an encrypted database on the
    production droplet. Still no real user data, but the account that would hold
    it now exists end to end.

**The one thing that did NOT behave as the plan's own brief predicted, stated
plainly rather than smoothed over.** The brief said the pre-tap screen shows
sample data and "the streak drops to 1" on the first tap. **The streak does not
drop. It is 1 before and 1 after.** Task 5's fix put `0` into `MISSED` so today
is unwalked in the sample, and the day before today is walked, so the sample
streak is already exactly one day; the real database then holds exactly one
day. Two different single days, the same number. The walkthrough's point — that
the sample history was never yours — is made by the 30-day percentage (77% → 3%)
and the 14-day row (9 walked → 1), not by the streak.
`docs/local-dev.md` now says so, and says which panels to point at instead.

The local `devtwo.db` was deleted after the walkthrough; no `*.db` other than
the tracked `fake-real.db` decoy is in the tree or staged.
