## What shipped
A pee tracker, on one screen that works the same on a phone and on a computer.

Today's count sits at the top as a single large number, with a big button
under it that logs one more. Every tap counts on its own — tap it as many
times as you go — and the number moves the moment it is saved, without the
page reloading or jumping. The count covers midnight to midnight, so it starts
again at zero each morning on its own.

Below that, a bar chart of the last seven days, one bar per day, with today's
bar picked out so you can see at a glance whether today is running high or
low. The daily average across those same seven days sits beside the chart's
title and is drawn across the bars as a dashed line, so you can see which days
were above it without doing the comparison in your head.

The time of each tap is recorded quietly and shown nowhere.

## Built differently
**The week starts when you do.** For the first few days the chart shows only
the days since your first tap rather than padding out to seven — days before
the tracker existed are not days you logged nothing, so they are left out
rather than drawn as zeros. When it is averaging fewer than seven days it says
so underneath. A day you skip AFTER starting does show as zero, because that
one is real.

**The average is drawn onto the chart as well as printed beside it.** You
asked for it alongside the seven days; a number sitting next to a chart is
still a comparison you have to do yourself, so it is also a dashed line across
the bars. It is the average of exactly the bars you are looking at, today
included — which does mean it reads a little low first thing in the morning,
while today is still only part of a day.

**On the first day, and on a week with nothing in it, no average is shown.**
On day one an "average" would just be today's count printed twice, and on an
empty week it would be a zero over a panel that already says nothing was
logged. The chart and the average appear together or not at all.

## Notes for the next build
**There is no way to take a tap back.** v1 asks for a log button and nothing
else that writes, so the route accepts `add` and 400s on anything else,
including the `remove` arm the route template ships. This is a plausible first
thing run10 asks for once they have used it. If it arrives: `pee_logs` already
declares an `id` for exactly that reason, so it is a route change and a
control, not a migration. run9's dashboard has the worked version of it,
including the not-below-zero bound living inside the DELETE statement rather
than in a read-then-write.

**`pee_logs.day` is decided at WRITE time and stored — never recompute it from
`at`.** The route resolves the friend's day from the browser's zone and files
the row under it, which is the settled pattern (friend-timezone ledger T1/T4).
Deriving the day from `at` at read time would silently re-file old rows the
first time they log from another country, and every panel would need the
widen-and-filter dance `users/devone/queries.ts` does. It is also why every
function in `queries.ts` takes a day key as a parameter and touches no zone at
all — the only zone-sensitive step in this dashboard is the route, so the
timezone and midnight-rollover assertions live in
`tests/routing/peeLogRoute.test.ts` rather than in this folder's own suite.

**`dailyAverage` takes the trend array, not the database, and that is
load-bearing.** The average is drawn as a reference line ON the chart, so a
second query could put the line somewhere the bars contradict while both were
individually correct. Keep it a function of the same array the component hands
to `TrendChart`; `queries.test.ts` asserts that as a property, not just for
one fixture.

**run10's average includes today; run9's excludes it.** Two nearly identical
dashboards that deliberately differ, because the two specs asked different
questions — run9 asked for a baseline to read today against, run10 asked for
the average of the seven days on the chart. Do not "fix" one to match the
other without going back to the spec that asked for it.

**`001_initial.sql` is frozen the moment this branch merges.** A fix is `002`
plus a data-survival test in the same commit.

**`TrendChart.tsx` is a client component under `users/` and
`tests/users/noLocalDay.test.ts` does not see it.** That sweep names
`dashboard.tsx` and `queries.ts`; a third `.tsx` in a user folder is unswept.
This one reads no clock — every day, count and label arrives resolved from
`queries.ts` — but nothing enforces that. Widening the sweep to
`users/*/*.tsx` would close it, and would cover run9's copy at the same time.

**The chart guard is what makes Recharts allowed here at all**
(docs/dashboard-build-rules.md §3, arm 2: data-computing components are
sanctioned only when degenerate data renders the empty state instead).
`chartable` in `dashboard.tsx` must keep gating it, and
`users/run10/tests/dashboard.test.ts` is what holds that. The ruling names
"all-identical" as degenerate; this build reads that as `max === 0`, because a
zero-based bar domain of `[0, n]` charts a week of identical non-zero days
perfectly well and blanking it would hide a plausible week.

**The container caps at 672px, not the guidelines' 1200px.** A deliberate
deviation, commented at the call site: two panels in a spec-fixed vertical
order, a tap target and seven bars, none of which improve by being stretched
across a desktop. If a future version adds a third panel this is the first
thing to revisit — the reasoning is about these two panels, not about the
dashboard forever.

**The count does not pop when it changes.** `lib/ui/WriteAction.tsx` patches
the value in place when the server confirms, which satisfies the "nothing
moves before the write lands" half of the guidelines, but the number itself
does not animate on arrival. Doing that needs client state holding the
previous value, which is a bigger change than it looks and would sit on the
one path that must never be able to throw.
